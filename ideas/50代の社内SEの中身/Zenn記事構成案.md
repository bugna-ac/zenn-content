# 構成案
本文側の見出しや小見出し案も一緒に整理して。この記事の目的は、変遷だけなのだが、もう一つの記事では、生成AIによるプログラム作成では、ユーザは結局上ソフトウェア工学の上流側の設計から外れていないかを監視し、設計の改善を生成AIにアドバイスをもらう体制になるのでは、という内容を書きたい。
つまりこの記事は、上流側に気づいた過去の経験から、現時点での生成AIによるシステム開発論の序論を書きたい。Zenn向けに。

この記事は「上流に気づいていくまでの個人体験」を軸にして、次の記事で「生成AI 時代の上流設計論」につなぐ構成にすると流れがきれいになる。[1]

### 見出しレベル構成（H2/H3）

#### 1. はじめに：なぜ今「上流」を振り返るのか

- 生成AIでコードを書く時代に、「そもそもの設計」をどう扱うかが気になっていることを書く。  
- この記事は、上流に気づくまでの自分の変遷を整理し、次の記事で「生成AI×上流設計」の話につなぐ序章であると明示する。[1]

#### 2. 手続き型の世界：コードだけを見ていた頃

- Fortran77 / 汎用機 / RS6000 でのサブルーチン開発と、Visual Basic による業務アプリの時代。[1]
- 「一人一台PC」「OAブーム」の中で、目の前の処理を書くことが中心で、業務全体や上流はほとんど意識していなかった、というニュアンスを書く。[1]

#### 3. オブジェクト指向とのすれ違い：憧れと挫折

- Java 好きの先輩が現れ、オブジェクト指向という言葉だけが先に入ってきたが、自分には遠く感じていたこと。[1]
- 本屋で Rational Rose / Visual Modeler を見つけ、「図からコード生成」という魔法に惹かれたが、ツールも概念も使いこなせずモヤモヤだけが残ったこと。[1]
- OSS GIS + Python2 への挑戦も含め、「仕組みを理解したい気持ち」と「言語やツールへの拒否感」が同居していた時期としてまとめる。[1]

#### 4. チーム開発と部品化で気づいたこと

- VB.NET / .NET 1.0/2.0 への移行で、「現代的な開発」として DLL 分割・部品再利用・少人数チーム開発を経験した話。[1]
- JUDE などの UML ツールで構成図を書くようになり、「コードの中身」だけでなく「全体構成」「部品のつながり」を意識し始めたことを書く。[1]
- ここでのポイントは「オブジェクト指向の文法」より「構造化・再利用・分割統治」の価値に触れたこととして整理する。[1]

#### 5. UML・GTD・ドラッカーで「上流」に目が向いた

- UML をきっかけに、マインドマップ（FreeMind）で要求を洗い出し、ユースケース図に落としていく流れを身につけたこと。[1]
- GTD によってコンテキスト別のタスク管理を始め、「自分の頭の中の状態」を設計し直す感覚を得たこと。[1]
- ドラッカーの「マネジメント」と「7つの習慣」から、外部要件と内部要件を分けて捉える視点を得て、「オブジェクト指向はプログラミング言語だけの話ではない」と感じ始めたことを書く。[1]

#### 6. 建設業界とアジャイルで見えた「本当の課題」

- 2000年以降、技術開発と建設業界の現場のギャップに向き合い、「現状把握の弱さ」「要求の曖昧さ」「アウトプット偏重」の問題を痛感したこと。[1]
- 本質課題が「原価・納期・人材減少・経験値バンクの縮小」にあると見えつつ、バズワード的な技術導入で利益が溶ける構造への違和感を書き出す。[1]
- アジャイルを「小さな成果の積み上げ」「プロダクトマネジメントと技術選定」「外部要因の衝撃分散」として捉えるようになったことを整理する。[1]

#### 7. いま考えていること：生成AIと上流設計へのつながり

- ここは「次の記事」へのブリッジだけを書く短いセクションにする。  
- ポイント:
  - コードを書く部分は生成AIにかなり任せられるようになった。  
  - しかし、「何を作るか」「どんな制約・構造で作るか」「業務や組織との整合」を考える上流は相変わらず人間側に残っているのではないかという仮説を提示する。  
  - 自分の遠回りの経験から、「生成AIの役割は、コード生成だけでなく、上流設計のレビューと改善提案にこそ置くべきでは？」という問いを投げて終える。[1]

## 第7節「いま考えていること：生成AIと上流設計へのつながり」案

### 7. いま考えていること：生成AIと上流設計へのつながり

ここまで振り返ってみると、自分のキャリアは一貫して「コードそのもの」から少しずつ離れ、「何を作るか」「どう組み立てるか」という上流寄りの問いに近づいてきたとも言える。Fortran77 や Visual Basic で目の前の処理だけを書いていたところから、UML やマインドマップで業務を見える化し、GTD やドラッカーで自分自身のタスクや役割を設計し直し、さらにアジャイルやプロダクトマネジメントで組織や業界レベルの構造を気にするようになっていった。[1]

今の生成AIブームを見ていると、かつて Rational Rose や Visual Modeler に感じた「図からコードが出てくる魔法」に、とてもよく似た期待を重ねてしまう。違うのは、当時はスケルトンコードしか出てこなかったのに対して、現在の生成AIはかなりそれっぽい実装まで一気に吐き出してくれるところだろう。[1]
ただ、自分の感覚では、コード生成がどれだけ賢くなっても、「どんなモデルで世界を切り取るか」「どこまでをシステム化し、どこからを人間や他部署に委ねるか」といった上流の判断は、依然として人間側の責任として残り続けるのではないかと感じている。[1]

むしろ、生成AIは「コード職人の代わり」ではなく、「上流設計が崩れていないかを一緒に監視し、改善案を出してもらう相棒」として使った方が力を発揮するのではないか。例えば、ユースケース図や業務フロー、制約条件のメモを投げて、「この前提で本当にフィットする設計になっているか」「別の分割や抽象化はないか」といった問いをAIにぶつけ、設計のオルタナティブを一緒に検討するような使い方である。[1]

次の記事では、今回振り返ったような「手続き型から上流志向への遠回り」を踏まえつつ、生成AIと人間がソフトウェア工学のどのレイヤーを分担すべきか、特に上流設計とプロダクトマネジメントの境界をどう引くべきかについて考えてみたい。生成AIが「図からコード」だけでなく、「設計から改善提案」まで担う時代に、社内SEはどの位置に立てるのかを探っていく。[1]

## 第7節「いま考えていること：生成AIと上流設計へのつながり」（やわらかめ版）

ここまで振り返ってみると、自分のキャリアは、少しずつ「コードそのもの」から離れてきたように思います。Fortran77 や Visual Basic で目の前の処理だけを書いていたところから、UML やマインドマップで業務を図にし始め、GTD やドラッカーで自分のタスクや役割を整理し、アジャイルやプロダクトマネジメントで組織や業界の構造まで気にするようになってきました。[1]

今の生成AIの盛り上がりを見ていると、昔の Rational Rose や Visual Modeler に感じていた「図からコードが出てくるなんて、そんなことある？」というワクワクと、どこか重なります。違うのは、当時のツールはスケルトンコード止まりだったのに対して、今のAIはかなり実用レベルのコードまで出してくれるところです。[1]
とはいえ、どれだけAIがコードを頑張ってくれても、「どんなモデルで世界を切り分けるか」「どこからどこまでをシステム化するか」「どこを人間や他部署に任せるか」といった判断は、そう簡単には自動化できないのではないか……という感覚もあります。[1]

むしろ、生成AIには「コード職人の完全な代わり」になってもらうのではなく、「上流の設計がブレていないか、一緒に見張ってもらうパートナー」になってもらう方が良さそうだと感じています。ユースケース図や業務フロー、制約条件のメモをAIに投げて、「この前提でこの設計は筋が良いか」「別の分割や抽象化の案はないか」を相談するような使い方です。[1]

次の記事では、ここまでの「手続き型から上流志向への遠回り」を踏まえて、生成AIと人間がソフトウェア工学のどのあたりを分担すると気持ちよく働けるのかを考えてみます。特に、上流設計やプロダクトマネジメントのどこまでをAIに手伝ってもらい、どこから先は人間が腹をくくるべきなのか、その境界線を探ってみたいと思います。[1]
