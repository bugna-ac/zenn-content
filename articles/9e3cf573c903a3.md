# 変遷図
![](images50代の社内SEのパソコン履歴（だけの記事）-2026-01-12-05-15-21.png)
# 1.はじめに：なぜ今「上流」を振り返るのか
生成AIでコードを書いていると、困ったことがたくさん起きることを書いた。
https://zenn.dev/bugnabuna/articles/6bc9775186eaf7
**恒久対策として「人間が上位ユースケースと部品分割を考え、Rooには小さい部品単位でコード生成を頼む」というAI最適化設計** というのが主張である。

**「そもそもの設計」は人間が考える** 、はバイブコーディングをするにも、原則だと考えているが、生成AIの早いサイクルに巻き込まれると、コードやAPIがどんどんできてしまい、設計との整合性は、動いているからいいっしょ、とタイパ重視からも思考を止めてしまうことが起きやすい。

**設計は人間** が握ることは変わらない考えである。

考えを巡らしていると、自分の過去が頭をよぎり、まとめてみた。上流側に気づくまでの自分の変遷と、今の生成AIでコードを書く今と、同じ流れの中にいることを確認し、別の記事で「生成AI x 上流設計」の話に繋げたい。

# 2.手続型の世界：コードだけをみていた頃
Fortran77 / 汎用機 /RS6000 と機械は変われど、先輩の指示や過去のコード財産を活用するための、サブルーチンを書いていた。

建設業という業種なので、対象にするコードは優秀な先輩技術者が書いたので目的は明確、作業は後処理用のサブルーチンが多かった。

社内のOA推進が進み、一人一台PCになり、オフィススイートの使いこなし派が多数の中、私はVisual Basicで業務アプリを作成。まだ業務全体や上流を意識した業務はやっていない。

# 3.オブジェクト指向とのすれ違い：憧れと挫折
Java好きの先輩が入ってきて隣でオブジェクト指向を唱えていた。VBにVisual ModelerというRational Rose（ビジュアルモデリングツール：UML）のサブセットが加えられた。「図からコード生成」という魔法に惹かれたが、ツールも概念も使いこなせずモヤモヤだけが残った。

業務で、GIS（地理情報システム）を使い始め、社内環境変化を狙って、プロプライエタリ環境から、FOSS4G（Free and Open Source Software for Geospatial）を使い始めた。豊富なプラグインは、Python2で書かれていて、OSS GIS + Python2 への挑戦も含め、「仕組みを理解したい気持ち」と「言語やツールへの拒否感」が拭えなかった。

# 4.チーム開発と部品化で気づいたこと
VB.NET / .NET 1.0/2.0 への移行して、「現代的な開発」として DLL 分割・部品再利用・少人数チーム開発を経験した。

GISは、地図表示のビジュアルな部分、データ格納のRDB、内部的な科学計算、ファイル入出力、などで構成される。これをメインとマネージDLLでチームを分けて開発し、更新はDLL差し替えで行った。

チーム内では、DLLの関数呼び出しの引数が分かれば良いので、ガッツリと上流を意識しなくても開発が行えたが、当時のJUDE(現astah*)でUML1.4を使って、配置図を描いた。
この時に、はじめて全体構成」「部品のつながり」を意識した。

構造化、再利用、分割統治を行ったことで、メンバーが自分のペースや考えで、改善ができ、公開APIが変わらなければ、動くアプリケーションになるプロジェクトマネジメントに取り組む気持ちが軽くなった記憶がある。

# 5.UML・GTD・ドラッカーで「上流」に目が向いた

UML をきっかけに、マインドマップ（FreeMind）で要求を洗い出し、ユースケース図に落としていく流れを身につけた。

同時期に広く関心を集めた、GTD(Gettings Things Done) によってコンテキスト別のタスク管理を始め、「自分の頭の中を空にする仕事術」によって、開発する機能を客観的な条件で設計し直す感覚を得たこと。

また、ドラッカーの「マネジメント」とコビィーの「7つの習慣」から、外部要件と内部要件を分けて捉える視点を得て、「オブジェクト指向はプログラミング言語だけの話ではない」と感じ始めたことは、大きな転機であった。仕事も下記の余談にあるような、世の中の要求とシステムの有り様のすり合わせ検討が多くなったのも一因である。

:::details（余談）統合型GIS
阪神淡路大震災後で、GIS活用は注目を集め、地上も地下もGISによるデータ集約とインテグレーションがたくさんの委員会で検討された。

GISのシステム面は3層アーキテクチャ構造で、プレゼンテーション層（地図描画UI）、アプリケーション層（計算・ビジネスロジック）、データ層（RDB・空間DB）に分かれ、WebGISを含め現在でも大きく変わらない。

そのため、GIS活用検討の場面では、「誰が」「いつ」「どこに」「何を」「どれくらいの更新頻度」で更新し、「誰に利用権利を与えるか」、という「権限・責任分担（ガバナンス）設計」と「セキュリティ／アクセス制御を含む非機能要件定義」がほとんどである。

建設業は、目的構造物は施主の持ち物で、施工した建設業者は施工後にメンテナンス契約がなければ、構造物に権利を持つことがない（瑕疵担保を除く）。
※作るための設計図書も、施主のものである。

施主は、国・地方公共団体・独立行政法人・公社などの公的機関と、民間企業・個人になるため、統一的なルールでデータが集められるわけではない。データ提供者になる施主が自分でお金をかけてまで、データを提供するメリットがなければ、かかる経費が無駄になるからである。

この時に必要になるのが、GISを使ったソリューションの上流側の目的を明確にすることになる。
:::
# 6.建設業界とアジャイルで見えた「本当の課題」

2000年以降、いつも感じるようになったのは、会社方針としての「現状把握の弱さ」「要求の曖昧さ」「アウトプット偏重」である。

特に、技術開発をしていると建設業界の現場感覚とのギャップを常時感じていて、いまだに引きずっている。

当時は、建設省が国土交通省に再編された時で、CALS/EC・情報化施工・電子入札・電子納品などへの取り組みが進んでいました。

建設CALS（建設CALS/EC）は、「公共事業の情報を電子化し、ネットワークで交換・共有・連携する業務効率化を目的にしていて、世の中の流れに乗った取り組みでした。

本質課題が「原価・納期・人材減少・経験値バンクの縮小」にあると見えつつ、バズワード的な技術導入で利益が溶ける構造への違和感を書き出す。

アジャイルを「小さな成果の積み上げ」「プロダクトマネジメントと技術選定」「外部要因の衝撃分散」として捉えるようになったことを整理する。
